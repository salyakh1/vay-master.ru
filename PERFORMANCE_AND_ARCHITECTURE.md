# Архитектура Vay-Master и план ускорения платформы

## 1. Как всё устроено сейчас

### Стек и данные

- **Frontend:** Next.js 14, React 18, Tailwind, Leaflet (карты).
- **Backend:** Supabase (PostgreSQL + Auth + Storage + RLS). Почти все запросы идут с клиента через `@supabase/supabase-js` (anon key).
- **Роли:** мастер, продавец, клиент; PRO-подписка (ограничения после пробной недели).

Почти все страницы — `'use client'`. Данные загружаются в `useEffect` вызовами `supabase.from(...)`. Серверных данных при первом рендере нет: ни `getServerSideProps`, ни `getStaticProps`, ни кэшей (`revalidate` / `unstable_cache`) не используется.

### Основные потоки данных

| Место | Откуда данные | Особенности |
|-------|----------------|------------|
| **Провайдер (Auth)** | `profiles` по `auth.user.id` | Один запрос при логине и по `onAuthStateChange`, без кэша. |
| **Главная** | `profiles` (stats), баннеры | Статистика подгружается при скролле до блока (Intersection Observer). |
| **Поиск мастеров** | `specializations`, `services`, `profiles`, геокод, `serve-location` | Много последовательных запросов: спец/услуги → profile_ids → по городу (город + геокод + serve-location) → основной запрос `profiles` с join. |
| **Лента (feed)** | `follows` → `portfolio_items` + мастер | Сначала подписки, потом портфолио; отдельно лайки и комментарии по всем item id. |
| **Публикации** | `portfolio_items`, `products` | Два больших запроса (+ фильтр по городу на клиенте). |
| **Товары** | `products` + `profiles` (seller) + категории | Один запрос с join; фильтр по городу продавца — на клиенте после загрузки. |
| **Профиль [id]** | `profiles`, портфолио, отзывы, товары, спецы, услуги, истории | Очень тяжёлая страница: много секций, частично Render-on-Demand (портфолио/отзывы по Intersection Observer). |
| **Заказы** | `orders` и связанные таблицы | Запросы по экрану и действиям. |
| **Чаты** | `chats`, `messages` | Классическая схема «список чатов + сообщения по выбранному чату». |

### API (Route Handlers)

Часть логики вынесена в API:

- **Geocode** — геокод по строке, с кэшем в БД (`geocoding_cache`).
- **Masters serve-location** — мастера, чей радиус покрывает точку (lat/lng).
- **Recommendations nearby** — товары в радиусе от мастера (для «Товары рядом»).
- **Recommendations products** — персонализированные товары.
- **Ads, banners** — реклама и баннеры.
- **Reviews, stories, activity, notifications** — свои route для отзывов, историй, активности, уведомлений.

Остальное (поиск, лента, товары, профиль, заказы, чаты) — прямые запросы из браузера в Supabase.

### Что уже хорошо для скорости

- **Dynamic import** тяжёлых частей: Leaflet, PortfolioGallery, CreateStory, модалки (Pro, калькулятор, жалобы и т.п.) — грузятся по необходимости.
- **Render-on-Demand** на главной (статистика), в поиске (справочники при открытии фильтров), в профиле (портфолио/отзывы при скролле).
- **Пагинация** на поиске, ленте, товарах, публикациях.
- **Геокод** кэшируется в БД.

## 2. Узкие места (почему не «очень быстро»)

### 2.1 Много мелких запросов под один сценарий

- **Поиск при фильтре по городу:** спецы → услуги → profile_ids по спецу/услуге → профили по городу → геокод → serve-location → основной запрос. 5–7 шагов, часть последовательно.
- **Лента:** follows → portfolio_items → лайки по user+item_ids → комментарии по item_ids. Четыре запроса на каждый запрос ленты.
- **Профиль:** десятки зависимостей (профиль, спецы, услуги, портфолио, отзывы, товары, истории и т.д.), часть — отдельными запросами.

Итог: большая задержка до «полной картинки» (TТFB + сумма задержек запросов).

### 2.2 Нет кэширования данных на клиенте

Каждый переход/обновление страницы — заново все запросы. Один и тот же профиль, те же товары, тот же поиск — без памяти. Браузер кэширует только статику и (если настроено) ответы API по заголовкам.

### 2.3 Тяжёлая фильтрация на клиенте

- **Товары:** выборка тянется без фильтра по городу, потом отбрасывание по `seller.city` на клиенте → лишние строки и трафик.
- **Публикации:** аналогично — город применяется в JS после загрузки.

### 2.4 Один очень большой компонент

`app/profile/[id]/page.tsx` — тысячи строк, всё в одном дереве. Любое изменение состояния может вести к дорогим ре-рендерам и усложняет разбиение на чанки.

### 2.5 Нет явного кэша и инвалидации на API

- **serve-location:** результат для пары (lat, lng) можно кэшировать на 5–15 минут.
- **Рекомендации, баннеры, справочники** — хорошие кандидаты на короткий cache (stale-while-revalidate).

### 2.6 Регион и «первый байт»

Vercel в `iad1` (США). Пользователи из РФ/СНГ получают большую задержку на первый ответ. Supabase в своём регионе — ещё одна сеть. Это напрямую влияет на ощущение скорости.

## 3. Как сделать платформу «очень быстро»

### Приоритет 1 — быстрые победы

1. **Кэш на API для стабильных данных**
   - `serve-location?lat=&lng=` — кэшировать ответ на 5–15 мин (Cache-Control или in-memory/Redis по ключу `lat,lng`).
   - Справочники (специализации, услуги, категории товаров) — отдавать с `Cache-Control: public, max-age=300` или через `unstable_cache` в Next и revalidate.

2. **Объединить шаги поиска при городе**
   - Один Route Handler, например `GET /api/search/masters?q=&city=&spec=&service=&page=`, внутри:
     - геокод города (уже с кэшем),
     - serve-location,
     - один запрос в Supabase с нужными фильтрами и join.
   - На клиенте — один `fetch` вместо цепочки из 5–7.

3. **Фильтр по городу в БД для товаров**
   - Не тянуть все товары и отфильтровывать по городу на клиенте. Либо подзапрос/join к `profiles` по `seller_id` и `city`, либо представление/функция в БД. Так меньше строк и трафика.

4. **Убрать дубли запросов**
   - В поиске уже убран дубль `in('id', finalProfileIds)`.
   - Проверить ленту и профиль: объединять «лайки + комментарии» в один запрос или в один RPC, где это возможно.

### Приоритет 2 — клиентский кэш и меньше воды

5. **React Query (TanStack Query) или SWR**
   - Обернуть загрузки списков (поиск, товары, лента, публикации) в `useQuery` с ключом по фильтрам и пагинации.
   - Включить `staleTime` (например 1–2 мин для списков, дольше для справочников).
   - Так повторные открытия страниц и возвраты «назад» будут мгновенными за счёт кэша, фоновое обновление — по настройке.

6. **Виртуализация длинных списков**
   - В зависимостях уже есть `react-window`. Подключить для:
     - выдачи поиска мастеров,
     - каталога товаров,
     - ленты и публикаций.
   - Рендерить только видимые элементы — меньше DOM и перерисовок при скролле.

7. **Кэш и предзагрузка для Auth**
   - Профиль пользователя из `profiles` кэшировать в React Query/SWR по `user.id`, с обновлением при логине/логауте и (опционально) при фокусе вкладки. Уменьшит лишние повторные запросы профиля.

### Приоритет 3 — архитектура страниц и данных

8. **Разбить профиль на подстраницы/табы**
   - Вынести «Настройки», «Портфолио», «Отзывы», «Товары» в отдельные route или в тяжёлые ленивые компоненты с чёткими границами. Меньше кода в одном модуле, точечнее загрузка и чанки.

9. **Серверные данные для «холодного» первого захода**
   - Для главной, поиска (без города или с дефолтным городом), каталога товаров сделать Server Components или `getServerSideProps`/аналог, который тянет первый слой данных на сервере и отдаёт HTML уже с данными.
   - Клиент подхватывает гидрацией и дальше работает как сейчас (фильтры, пагинация, кэш через React Query/SWR). Первый экран появляется быстрее.

10. **Батчинг и представления в БД**
    - Лента: по возможности один запрос (view или RPC), который возвращает портфолио с флагами «лайк текущего пользователя» и счётчиками, без отдельных запросов на лайки/комментарии на каждый рендер.
    - Аналогично — «список мастеров с числом отзывов и рейтингом» одним запросом вместо нескольких.

### Приоритет 4 — инфраструктура и доставка

11. **Регион и Edge**
    - Разместить приложение (Vercel/другое) в регионе ближе к основной аудитории (например EU или RU, если есть партнёр).
    - Критичные API (поиск, список товаров, рекомендации) при необходимости вынести в Edge/Worker с кэшем.

12. **Картинки и статика**
    - Уже используется `next/image` и `remotePatterns` для Supabase Storage. Добавить `sizes` под реальные брейкпоинты, при необходимости — blur placeholder и CDN перед Storage.

13. **Заголовки кэширования для API**
    - Для всех GET-маршрутов, где данные не персональные и не меняются каждую секунду, задать разумные `Cache-Control` (статика списков — минуты, рекомендации — десятки секунд). Это уменьшит повторные поездки в Supabase при навигации и обновлении.

---

## 4. Минимальный план на 1–2 недели

- Неделя 1:
  - Включить React Query (или SWR) для поиска, товаров и ленты.
  - Сделать единый `GET /api/search/masters` с геокодом и serve-location внутри.
  - Перенести фильтр по городу для товаров в запрос к БД (join/подзапрос по `profiles.city`).
- Неделя 2:
  - Кэш для `serve-location` и для справочников (специальности, услуги, категории).
  - Виртуализация списков на поиске и товарах.
  - Разнести профиль на отдельные подстраницы или тяжёлые ленивые секции.

После этого платформа будет ощутимо быстрее за счёт меньшего числа запросов, клиентского кэша, виртуализации и чуть более «умного» первого рендера. Дальше можно добавлять серверный первый кадр, Edge и тонкую настройку кэшей под метрики (LCP, TBT, время до интерактивности).
