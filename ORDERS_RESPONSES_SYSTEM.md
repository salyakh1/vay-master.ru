# Система откликов мастеров на заказы

## 📋 Описание

Полноценная система откликов мастеров на заказы с защитой от race conditions, транзакциями и уведомлениями.

## 🗄️ База данных

### SQL миграции

1. **`supabase/update_orders_responses_system.sql`**
   - Добавляет статус `open` для заказов
   - Создает триггеры для проверки лимита откликов (30)
   - Создает триггеры для проверки статуса заказа
   - Автоматическое обновление статуса заказа при принятии отклика

2. **`supabase/create_accept_response_function.sql`**
   - Функция `accept_order_response()` для атомарного принятия отклика
   - Защита от race conditions через `FOR UPDATE`
   - Транзакционная логика

### Выполнение миграций

```sql
-- 1. Выполните в Supabase SQL Editor:
-- supabase/update_orders_responses_system.sql

-- 2. Затем выполните:
-- supabase/create_accept_response_function.sql
```

## 🔌 API Endpoints

### 1. Создание отклика
**POST** `/api/orders/[id]/respond`

**Headers:**
```
Authorization: Bearer <token>
```

**Body:**
```json
{
  "price": "50000",  // опционально
  "message": "Готов выполнить работу качественно и в срок"
}
```

**Проверки:**
- Пользователь авторизован
- Роль пользователя = `master`
- Заказ существует
- Заказ не принадлежит мастеру
- Статус заказа = `open` или `new`
- Мастер еще не откликался
- Количество откликов < 30

**Ответ:**
```json
{
  "data": {
    "id": "...",
    "order_id": "...",
    "master_id": "...",
    "price": 50000,
    "message": "...",
    "status": "pending"
  }
}
```

### 2. Принятие отклика
**POST** `/api/orders/responses/[id]/accept`

**Headers:**
```
Authorization: Bearer <token>
```

**Проверки:**
- Пользователь авторизован
- Пользователь - владелец заказа
- Заказ еще открыт
- Отклик в статусе `pending`
- Исполнитель еще не выбран

**Действия:**
- Обновляет отклик на `accepted`
- Отклоняет все остальные отклики (`rejected`)
- Обновляет заказ: `status = 'in_progress'`, `selected_master_id = master_id`

**Ответ:**
```json
{
  "message": "Отклик принят",
  "data": {
    "orderId": "...",
    "masterId": "..."
  }
}
```

## 🔔 Уведомления

### При отклике мастера:
Заказчик получает сообщение в личный чат от системного пользователя:
```
На ваш заказ откликнулся мастер [Имя мастера].

Просмотреть отклик: [ссылка на заказ]
```

### При принятии отклика:
Мастер получает сообщение в личный чат от заказчика:
```

Клиент [Имя клиента] выбрал вас в качестве исполнителя.

Перейти к заказу: [ссылка на заказ]
```

## 🔒 Защита и ограничения

1. **Лимит откликов:** максимум 30 откликов на заказ (проверка через триггер)
2. **Статус заказа:** отклики принимаются только для статусов `open` и `new`
3. **Повторный отклик:** мастер может откликнуться только один раз (UNIQUE constraint)
4. **Транзакции:** принятие отклика выполняется атомарно через функцию PostgreSQL
5. **Race conditions:** защита через `FOR UPDATE` в функции принятия
6. **Валидация:** все проверки выполняются на сервере

## 📊 Статусы

### Заказы:
- `open` - Открыт, принимает отклики (новый дефолтный статус)
- `new` - Новый (legacy, для совместимости)
- `in_progress` - В работе (исполнитель выбран)
- `completed` - Выполнен
- `cancelled` - Отменен

### Отклики:
- `pending` - Ожидает решения
- `accepted` - Принят (мастер выбран)
- `rejected` - Отклонен

## 🚀 Использование

1. **Мастер откликается:**
   - Открывает заказ
   - Нажимает "Откликнуться"
   - Заполняет форму (цена опциональна, сообщение обязательно)
   - Отправляет отклик

2. **Заказчик принимает отклик:**
   - Видит список откликов
   - Нажимает "Принять" на нужном отклике
   - Подтверждает в модальном окне
   - Заказ переходит в работу, остальные отклики отклоняются

3. **После принятия:**
   - Заказ переходит в статус `in_progress`
   - Другие мастера не могут откликаться
   - Заказчик и мастер могут общаться в чате

## ⚠️ Важные моменты

1. **Все проверки на сервере** - клиентская валидация только для UX
2. **Транзакции** - критичные операции выполняются атомарно
3. **Уведомления** - отправляются асинхронно, не блокируют основной поток
4. **RLS политики** - все операции защищены Row Level Security
