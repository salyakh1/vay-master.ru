# Полный анализ проекта VAY-MASTER

**Дата:** 04.02.2026  
**Цель:** Архитектура, стек, бизнес-логика, риски и рекомендации.

---

## 1. Краткий вывод

**Стоит:** Да. Проект — зрелая B2B/B2C платформа (мастера ↔ клиенты ↔ продавцы) с чёткой монетизацией (заказы, реклама, PRO), админкой и современным стеком. Есть техдолг и точки роста по производительности и масштабированию.

**Жесткая правда:** Архитектура логичная, но часть логики размазана по клиенту (тяжёлые страницы search/products), миграции БД накопились (50+ SQL файлов), нет тестов и CI. Для роста выручки и нагрузки нужны: серверные списки, кэш, мониторинг, упорядочивание миграций.

## 3. Архитектура приложения

### 3.1 Next.js App Router

- **Главная:** `app/page.tsx` (RSC) → подтягивает баннеры и категории мастеров через `lib/server-data.ts` (SSR) → рендерит `HomeClient.tsx` (client).
- **Остальные страницы:** в основном `'use client'` с данными через `useEffect` + Supabase или API routes.
- **Провайдеры:** `app/providers.tsx` — контекст авторизации (`useAuth`), сессия Supabase Auth, подгрузка `profiles`.

### 3.2 Данные и доступ

- **Клиент:** один инстанс `supabase` из `lib/supabase.ts` (anon key), RLS на всех таблицах.
- **Сервер:** отдельный клиент без сессии (`getServerSupabase()` в `lib/server-data.ts`) для баннеров и категорий; в API routes — `createClient` с `SUPABASE_SERVICE_ROLE_KEY` для обхода RLS где нужно (поиск, админка).

### 3.3 Роли пользователей

| Роль | Описание | Ключевые сценарии |
|------|----------|-------------------|
| **master** | Мастер (услуги) | Профиль, подкатегории/услуги, портфолио, отклики на заказы, PRO-подписка, геолокация и радиус |
| **seller** | Продавец | Товары, категории товаров, магазин, отзывы продавца, PRO |
| **client** | Клиент | Просмотр ленты, поиск мастеров/товаров, создание заказов, чаты, заказ товаров |

Роль задаётся при регистрации (`auth.user_metadata.role`), профиль в `profiles` с полями под каждую роль (master_*, seller_*, рейтинги, геолокация и т.д.).

## 4. Модель данных (основное)

### 4.1 Ядро (schema.sql + миграции)

- **profiles** — пользователи (id → auth.users), роль, контакты, описание, PRO, рейтинги, геолокация мастеров/продавцов.
- **posts** / **post_likes** — лента (контент, картинки, счётчик лайков).
- **products** — товары продавцов (категория/подкатегория, цена, остатки, рейтинг).
- **chats** / **messages** — чаты 1-на-1, поддержка изображений в сообщениях.
- **orders** / **order_responses** — заказы клиентов, отклики мастеров, статусы (new, in_progress, completed, cancelled), приём отклика, геокодинг (lat, lng, city).

### 4.2 Иерархия категорий (мастера)

- **categories** → **subcategories** → **services** (3 уровня).
- **profile_subcategories** / **profile_services** — привязка мастеров к подкатегориям и услугам.
- Заказы привязаны к категории (order.category и т.п.).

### 4.3 Товары (каталог)

- **product_categories** / **product_subcategories** — секции каталога (construction, exterior, tools, auto и т.д.).
- Продукты связаны с категорией/подкатегорией; есть маппинг специализаций к категориям товаров (`lib/specialization-product-mapping.ts`).

### 4.4 Дополнительные сущности

- **portfolio_items** — портфолио мастеров (лайки, комментарии, в т.ч. вложенные).
- **stories** / **story_views** — сторис с истечением срока.
- **ad_banners** — баннеры и контекстная реклама (типы: HERO_SPONSORED, INLINE_CONTEXT, SPONSORED_CARD и др., лимиты показов/кликов, регионы).
- **notifications** — уведомления (заказы, сообщения, система).
- **reviews** — отзывы по мастерам, товарам, продавцам + ответы (review_replies).
- **complaints** — жалобы (на пользователей/чаты), админка.
- **admin_roles**, **admin_permissions**, **admin_audit_logs**, **user_restrictions** — админка и модерация.
- **pro_subscriptions** / поля PRO в profiles — подписки и триал мастеров/продавцов.

## 5. API (app/api)

- **account/delete** — удаление аккаунта.
- **activity** — активность (items, seen, stats).
- **admin/** — категории, подкатегории, специализации, загрузка картинок, подписки, удаление пользователей, сообщения и т.д.; используется service role.
- **ads** — баннеры, клики/показы.
- **autocomplete** — подсказки (например, города).
- **banners** — баннеры по страницам, клики/просмотры.
- **categories**, **master-categories**, **specializations** — дерево и счётчики для мастеров.
- **chats** — удаление чата, mark-read, unread-count.
- **complaints** — жалобы.
- **geocode** — геокодинг адресов.
- **masters** — recommended, serve-location (для карты/радиуса).
- **notifications** — список, счётчик.
- **orders** — отклик на заказ, приём отклика (accept).
- **products** — комментарии к товарам (CRUD).
- **recommendations** — nearby, products (персонализация).
- **reviews** — отзывы и ответы.
- **search/masters** — полноценный поиск мастеров (текст, город, категория/подкатегория/услуга, пагинация), через service role.
- **stories** — CRUD, view (просмотр).
- **welcome-message** — приветственное сообщение.

Поиск мастеров и часть админки сознательно используют service role для обхода RLS и сложных запросов.

## 6. Ключевые сценарии (потоки)

1. **Главная (гость)** — баннеры и категории с SSR; быстрый поиск по товарам; CTA «Войти» и «Найти мастера».
2. **Главная (авторизован)** — Navbar, баннеры, категории, статистика (при скролле), быстрый поиск, переход в поиск мастеров/товары/заказы.
3. **Поиск мастеров** (`/search`) — фильтры (текст, город, категория/подкатегория/услуга), виртуализированный список карточек, врезки рекламы (AdSlot), сторис, рекомендации; данные через `/api/search/masters`.
4. **Товары** (`/products`) — секции категорий, фильтры, карточки товаров, карта магазинов, заказы, реклама; тяжёлая клиентская страница с react-window.
5. **Заказы** — создание заказа (`/orders/new`): категория, адрес (геокодинг), бюджет, фото; оплата за публикацию (200 ₽); список заказов; отклики мастеров и приём отклика.
6. **Лента** (`/feed`) — портфолио как посты, лайки, комментарии, сторис; виртуализация списка.
7. **Чаты** — список чатов, unread count, сообщения (в т.ч. изображения).
8. **Профиль** — просмотр мастер/продавец/клиент, портфолио, товары, отзывы, PRO-бейдж, карта/радиус для мастеров.
9. **Админка** (`/admin`) — отдельный layout, проверка `isAdmin` / `getAdminRole` (RPC к БД); разделы: пользователи, мастера, заказы, баннеры, жалобы, модерация, отзывы, подписки, настройки, безопасность, аналитика, изображения.

## 7. Монетизация и реклама

- **Заказы:** платная публикация заказа (200 ₽) — `OrderPaymentModal`, затем создание order.
- **PRO:** подписки и триал для мастеров/продавцов (`lib/masterAccess.ts`, `pro_until`, `is_pro`, `pro_trial_started_at`); админка управляет подписками.
- **Реклама:** система баннеров и слотов (см. AD_SYSTEM_ARCHITECTURE.md):
  - Типы: HERO_SPONSORED, INLINE_CONTEXT, SPONSORED_CARD, PROFILE_RELATED, FOOTER_BRAND.
  - Контекст: страница, категория, ключевые слова, регион, masterId.
  - Лимиты показов/кликов, даты, приоритет; учёт views/clicks в API.

## 9. Сильные стороны

- Чёткое разделение ролей и сценариев под мастер/продавец/клиент.
- Монетизация заложена: заказы, PRO, реклама с контекстом и лимитами.
- Современный UI (Tailwind, дизайн-система), виртуализация длинных списков.
- SSR на главной (баннеры, категории) для LCP.
- Полноценная админка с ролями и RPC для проверки прав.
- Богатая модель данных: категории 3 уровней, геолокация, отзывы, жалобы, сторис, портфолио.
- RLS включён на основных таблицах; чувствительные операции — через API с service role.

## 10. Слабости (что слабо)

- **Производительность и фронт**
  - Страницы поиска мастеров и каталога товаров тяжёлые: много логики и запросов на клиенте, большой JS-бандл. Страдает TTI и память на слабых устройствах.
  - Кроме главной, почти нет SSR/RSC для данных — списки подгружаются в `useEffect` после монтирования, первый контент появляется с задержкой.
  - Много прямых вызовов Supabase из компонентов — нет единого слоя кэша (React Query/SWR) и сложнее перейти на другой бэкенд.

- **База и миграции**
  - 50+ SQL-файлов в `supabase/` без явного порядка применения — риск «разъехавшейся» схемы при новом окружении или онбординге.
  - Нет скрипта «применить все миграции с нуля» или версионирования миграций.

- **Качество кода и надёжность**
  - Нет автотестов (unit/e2e) и CI — регрессии при рефакторинге и релизах ловятся вручную.
  - Дублирование типов (например, Complaint в `lib/supabase.ts` и `lib/admin.ts`) — риск расхождений с реальной БД.
  - В админке остались `console.log` при проверке прав — мусор в консоли и утечка деталей в проде.

- **Наблюдаемость и инфраструктура**
  - Нет мониторинга ошибок (Sentry и т.п.) и метрик по API — сбои и деградация обнаруживаются поздно.
  - Нет кэша для горячих данных (баннеры, категории) — лишняя нагрузка на БД при росте трафика.
  - Next.js 14.0.4 — отставание от актуальных патчей и фич.

- **Безопасность и операционка**
  - Использование `SUPABASE_SERVICE_ROLE_KEY` в API (поиск, админка) — ключ не должен утекать; нужна дисциплина и ревью эндпоинтов.
  - Нет явной политики ротации ключей и секретов, документированной в репозитории.

Итог: слабее всего — **клиентская тяжесть ключевых страниц**, **отсутствие тестов и CI**, **хаос с миграциями** и **отсутствие мониторинга**. Остальное — управляемый техдолг при планомерном исправлении.

## 11. Риски и техдолг

| Проблема | Влияние | Рекомендация |
|----------|---------|--------------|
| Тяжёлые клиентские страницы (search, products) | TTI, расход памяти, сложная отладка | Вынести списки в серверные API + пагинация; оставить виртуализацию на клиенте для уже подгруженных данных |
| 50+ SQL-миграций в supabase/ | Сложно воспроизвести окружение, порядок применения | Свести в 1–2 миграции с нуля или версионировать (например, одна папка migrations с порядком) |
| Нет автотестов и CI | Регрессии при рефакторинге | Добавить unit (Jest/Vitest) для lib и API; e2e (Playwright) для критичных сценариев; GitHub Actions |
| Дублирование типов (Complaint в lib/supabase и lib/admin) | Расхождения моделей | Вынести общие типы в один модуль (например, types/db.ts) |
| Прямые запросы к Supabase из компонентов | Сложнее кэшировать и переключаться на другой backend | Постепенно переводить на API routes или server components с server-data |
| Нет мониторинга и алертов | Сбои и деградация незаметны | Подключить Vercel Analytics, Sentry или аналог; метрики по API (latency, errors) |
| Статика Next 14.0.4 | Упуск исправлений и фич | Планово обновить до актуального 14.x и при необходимости до 15.x с проверкой совместимости |

## 12. Рекомендации по шагам

1. **Краткосрочно (1–2 спринта)**  
   - Зафиксировать порядок применения миграций (документ или скрипт).  
   - Добавить минимальный набор тестов (1–2 API routes, 1–2 функции из lib).  
   - Убрать или обернуть `console.log` в админке (проверка прав).

2. **Среднесрочно (1–2 месяца)**  
   - Перенести загрузку списков мастеров/товаров в сервер (API или RSC), оставив виртуализацию на клиенте.  
   - Ввести кэш (Redis или Vercel KV) для баннеров и категорий.  
   - Подключить мониторинг ошибок и базовую аналитику.

3. **Долгосрочно**  
   - Унификация типов и слоя данных.  
   - Обновление Next.js и ключевых зависимостей.  
   - Рассмотреть выделение критичных сервисов (поиск, рекомендации) в отдельные сервисы при росте нагрузки.

## 13. Структура репозитория (сводка)

```
app/           — страницы и API (App Router)
components/    — переиспользуемые UI-компоненты
lib/           — supabase, server-data, banners-server, admin, masterAccess, proSettings, маппинги
services/      — masters.ts (бизнес-логика мастеров)
supabase/      — schema.sql + миграции (таблицы, RLS, триггеры, RPC для админки)
public/        — статика (leaflet markers и т.д.)
```

Документация: README, QUICK_START, ENV_SETUP, AD_SYSTEM_ARCHITECTURE, ADMIN_PANEL_*, ORDERS_*, REVIEWS_*, NOTIFICATIONS_*, PORTFOLIO_*, BANNERS_* и др. — полезны для онбординга и поддержки.
